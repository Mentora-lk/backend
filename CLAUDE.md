# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Node.js/Express backend for Mentora, a tutoring platform. No ORM — all database access is raw SQL via the `pg` `Pool`. PostgreSQL is the only datastore.

## Commands

```bash
npm install       # install dependencies
npm run dev        # start with nodemon (auto-reload) — normal dev loop
npm start          # start without reload (production mode)
```

There is no test suite, lint config, or build step configured in `package.json` — don't assume `npm test` or `npm run lint` exist.

Server listens on `http://localhost:5000` by default (`PORT` env var). Health check: `GET /api/health`. There's also a live DB check at `GET /api/db-status` and a debug endpoint `GET /api/debug/check-user/:email` — but see the `app.js` caveat below, both are currently dead code and unreachable.

### Environment

Config is read directly from `process.env` in [src/config/env.js](src/config/env.js) and [src/config/db.js](src/config/db.js), loaded via `dotenv` from a `.env` file at the repo root (gitignored, not committed). Variables in use: `PORT`, `DATABASE_URL` (if set, used as the Postgres connection string with `ssl: { rejectUnauthorized: false }`, otherwise falls back to `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`), `JWT_SECRET`, `JWT_EXPIRES_IN`, `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET`, `EMAIL_USER`/`EMAIL_PASS` (Gmail SMTP via nodemailer), `FRONTEND_URL`, `GOOGLE_CLIENT_ID` (Google OAuth login, read directly in `googleAuthService.js` rather than via `env.js`), `CLIENT_URL` (Socket.io CORS origin, defaults to `*`).

## Architecture

**Layering:** routes → controllers → models, plus `services/` and `utils/`. Routes wire an Express `Router` to controller functions and attach `protect`/`authorize`/`restrictTo`/`multer` middleware. Controllers hold request handling and business logic (validation, hashing, Cloudinary uploads, SQL orchestration) inline — there's no separate service layer used consistently (`src/services/emailService.js` and `src/services/recommendationService.js` are mostly stubs/placeholders; real email sending goes through `src/utils/sendEmail.js`, not the service; `src/services/googleAuthService.js` is the one real, non-stub service). Models under `src/models/` are a mixed bag: `userModel.js` is a real query module, while `Course.js`, `Payment.js`, `Tutor.js` are empty placeholders and `Booking.js` documents the `bookings`/enrollment table shape as a JS object rather than exporting real queries — course/enrollment/community/course-review SQL actually lives directly inside the corresponding controllers, typically with dynamic `WHERE`-clause building and manual `$n` param indexing.

**Entry point / boot sequence:** [src/server.js](src/server.js) loads env, connects to Postgres (`connectDatabase`, exits process on failure), creates a raw `http.Server` wrapping the Express `app` (so Socket.io and Express share one port), calls `initSocket(httpServer, app)`, then starts listening.

**App wiring — read the whole file before editing it:** [src/app.js](src/app.js) mounts routers by prefix: `/api/auth`, `/api/users`, `/api/tutors`, `/api/students`, `/api/courses`, `/api/enrollments`, `/api/payments`, `/api/admin`, `/api/tutor` (tutor community), `/api/student` (student community). Note the near-identical singular/plural prefixes (`/api/tutors` vs `/api/tutor`, `/api/students` vs `/api/student`) mounting completely different route files — easy to typo into the wrong one. The file has **two `module.exports = app` statements** (line 67 and line 145) from incremental edits: because the first `module.exports` doesn't halt execution, everything registered after it — the second, more detailed 404 handler, the global error-handling middleware, `GET /api/db-status`, and `GET /api/debug/check-user/:email` (which returns password-hash metadata for a user by email) — is still added to the middleware stack but is **unreachable**, because the *first* 404 handler (line 63) catches every unmatched route before Express ever gets there. Effectively: no global error handler is active, and neither debug route responds. When adding routes/middleware here, add them before the first `module.exports` or they'll never run.

**Auth:** JWT-based. `protect` (in [src/middleware/authMiddleware.js](src/middleware/authMiddleware.js)) reads `Authorization: Bearer <token>`, verifies with `JWT_SECRET`, and attaches the decoded `{ id, role }` payload as `req.user`. Role gating exists in two parallel forms — `authorize(...roles)` (also in authMiddleware.js) and `restrictTo(...roles)` (in [src/middleware/roleMiddleware.js](src/middleware/roleMiddleware.js)) — both do the same thing; different route files pick one or the other, so match whichever the surrounding route file already uses. Some routers apply `protect` but never call `authorize`/`restrictTo` at all (e.g. enrollment status updates), so any authenticated user of any role can hit them — check each route file's middleware chain rather than assuming role-gating exists just because `protect` is present. Tokens are minted with `generateToken(id, role)` in [src/utils/jwtHelper.js](src/utils/jwtHelper.js).

**Google OAuth login:** `POST /api/auth/google` → `loginWithGoogle` in `authController.js` → [src/services/googleAuthService.js](src/services/googleAuthService.js). Verifies the Google ID token via `google-auth-library`, then either logs in a matching existing user by email or — if a `role` (`'student'`|`'tutor'`) is supplied — creates a new account with a random unused password hash plus a minimal profile. Throws `GoogleAccountNotFoundError` (map to 404) when no account exists and no role was given, so the frontend can prompt for a role and retry.

**Real-time (Socket.io):** [src/socket.js](src/socket.js) exports `initSocket(httpServer, app)`, attaches Socket.io to the same HTTP server, exposes the `io` instance via `app.locals.io`, and requires a valid JWT in `socket.handshake.auth.token` for every connection. Every socket auto-joins a personal room `user:<id>` on connect; community "rooms" are named `community:<communityId>` and joined/left via `join_community`/`leave_community` events. Only the tutor-community and student-community controllers currently emit to sockets (e.g. new post, new membership request, deadline created, request-status updates) — most other controllers don't touch `req.app.locals.io` at all.

**File uploads:** `multer` with `memoryStorage()` is configured per-route (not centrally), then buffers are streamed to Cloudinary via `uploadToCloudinary(buffer, folder, fileName?)` in [src/utils/cloudinaryUpload.js](src/utils/cloudinaryUpload.js), which resolves to a `secure_url` string to store in Postgres. Different routes use different multer configs for the same kind of upload — e.g. tutor registration uses `upload.fields([...])` with named fields (`profilePicture`, `banner`), while tutor-community posts use `upload.any()` and then copy the first file onto `req.file` for compatibility. Some routes attach multer middleware the controller never reads (e.g. course create/update accepts a `banner` file field but the controller only reads `req.body.image`) — check the controller body, not just the route, before assuming an upload is wired end-to-end. Match the existing pattern in the specific route file rather than introducing a third convention.

**Database access:** `src/config/db.js` exports `{ pool, query, connectDatabase }`. Most controllers call `db.query(sql, params)` directly with parameterized (`$1, $2, ...`) queries, though some (`studentController.js`, `studentCommunityController.js`) destructure `{ pool }` and call `pool.query(...)` instead for the same thing — no functional difference, just inconsistent style between files. There's no query builder or migration tool in this repo. Root-level scripts like [db-update.js](db-update.js) (adds a `post_reactions` table and a `poll_options` column if missing — run manually with `node db-update.js`, not wired into the app), `schema_check.js`, `list-tables.js`/`list_tables.js`, and the `check_*.js`/`scratch/*.js` files are ad hoc one-off scripts for inspecting/patching the live schema, not part of the app runtime.

**Profile endpoints are triplicated — check all three before changing "my profile" behavior.** There are three independent, inconsistent implementations of "get/update the logged-in user's profile":
- `GET/PUT /api/users/profile` ([userRoutes.js](src/routes/userRoutes.js) → `userController.js`, `protect` only, no role restriction) — branches internally on `req.user.role` and calls `userModel.getStudentProfile`/`getTutorProfile` or the `update*` equivalents, and is the only one of the three that handles a profile-picture upload via multer + Cloudinary.
- `GET/PUT /api/students/profile` ([studentRoutes.js](src/routes/studentRoutes.js) → [studentController.js](src/controllers/studentController.js), `protect + authorize('student')`) — inline `pool.query`, different field names than userController (`name`/`grade` vs `fullName`/`gradeLevel`), and returns richer live stats (`classesEnrolled`, `activeClasses`, `pendingApprovals`, `sessionsAttended`, `subjectsStudying`, `avgRatingGiven`) computed via subqueries against `enrollments`/`reviews`/`courses`.
- `GET/PUT /api/tutors/profile` ([tutorRoutes.js](src/routes/tutorRoutes.js) → `tutorController.js`, `protect + authorize('tutor')`) — the tutor-side analog, also independent of userController's tutor branch.

All three read/write the same `student_profiles`/`tutor_profiles` tables but with different field sets and different response shapes, so a fix to one does not propagate to the others. Confirm which endpoint the frontend actually calls before touching profile logic — don't assume `/api/users/profile` is authoritative just because it's role-generic.

**Enrollment quirks worth knowing before touching `enrollmentController.js`:** `POST /api/enrollments/test-email` is a real, unauthenticated route (a Postman testing leftover). `GET /me` and `GET /mine` are duplicate aliases for the same handler (as are `/schedule` and `/me/schedule`) because the frontend has two divergent service files calling different paths. `PATCH /:id` (status update) has no ownership or tutor-role check — any authenticated user can update any enrollment. New enrollments are inserted with status `'requested'`, not `'pending'` — match this exactly if adding status-dependent logic, since there's a DB `CHECK` constraint tied to it.

**Community feature split:** "Community" functionality is split into two independent controller/route pairs by role — `tutorCommunityController`/`tutorCommunityRoutes` (mounted at `/api/tutor`, uses `db.query`) for tutors managing communities, posts, membership requests, and deadlines, and `studentCommunityController`/`studentCommunityRoutes` (mounted at `/api/student`, uses `pool.query`, `restrictTo('student')`) for the student-facing side (discover/request/cancel membership, feed, reactions, deadline submissions). They are not a shared module — check both when a change should apply to both roles. On the tutor side, `router.use(protect)` is applied globally but `authorize('tutor')` is commented out as a TODO, so any authenticated user (including students) can currently hit tutor-community endpoints.

## Known rough edges (real, not to "fix" silently)

- [src/app.js](src/app.js) has two `module.exports = app` statements, leaving the global error handler, `/api/db-status`, and `/api/debug/check-user/:email` unreachable dead code (see above). Read the whole file before editing it.
- The `/api/users/profile`, `/api/students/profile`, and `/api/tutors/profile` triplication (see above) — these will drift further apart if only one is patched.
- Several `src/models/*.js` files are empty placeholders (`Course.js`, `Payment.js`, `Tutor.js`) — don't assume a model file's existence means it's used; grep for the actual query in the relevant controller.
- `src/services/emailService.js` is a no-op stub; the code path actually used for sending mail is `src/utils/sendEmail.js` (nodemailer, Gmail).
- [src/utils/validators.js](src/utils/validators.js) is a placeholder (`validate()` does nothing) — not wired into any route; don't assume input validation happens there.
- [src/middleware/errorMiddleware.js](src/middleware/errorMiddleware.js) is never `require`'d by `app.js` (whose own error handler is dead code too — see above) — nothing in this app currently has a working centralized error handler.
- README.md documents a `src/uploads/` folder for local file storage; it doesn't exist — all uploads go through Cloudinary (`src/utils/cloudinaryUpload.js`).
